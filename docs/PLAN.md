# ブラウザ版アステロイド（1〜4人・サーバーレス対戦）実装プラン

## 1. 要件

| # | 要件 | 対応方針 |
|---|------|----------|
| R1 | Atari「Asteroids」風のゲーム | ベクター風描画（線画）、慣性移動、画面端ループ、小惑星の分裂 |
| R2 | ブラウザで遊べる | HTML5 Canvas 2D + TypeScript。静的ファイルのみで動作 |
| R3 | 1〜4人で遊べる | ソロ / ローカル同一画面 / オンラインP2P の3モード |
| R4 | 小惑星を破壊して得点を競う | 小惑星サイズ別の得点、プレイヤー別スコア表示 |
| R5 | 相手プレイヤーを攻撃できる | 弾が他プレイヤーの船に当たると撃破＋得点 |
| R6 | 複数プレイの通信にサーバーを使わない | WebRTC DataChannel によるP2P。シグナリングは手動（コピペ/QRコード） |

## 2. 「サーバーを使用しない」通信の実現方法と制約（重要）

ブラウザ同士で直接通信できる現実的な手段は **WebRTC DataChannel** のみです。
WebRTC は接続確立時に「SDP（offer/answer）」を相手と交換する必要があり、
通常はシグナリングサーバーで行いますが、今回は **テキストを手動で受け渡す** 方式にします。

### 接続手順（ホスト＋最大3ゲスト、スター型）
1. ホストが「部屋を作る」→ ゲスト枠ごとに offer コードを生成
2. offer コードを LINE/Discord 等やQRコードでゲストに渡す
3. ゲストが貼り付け → answer コードを生成してホストに返す
4. ホストが answer を貼り付け → 接続完了（ゲスト人数分繰り返す）

- ICE候補は全て収集し終えてから（non-trickle）SDPに含めるため、交換は1往復で済む
- SDP は `CompressionStream`(deflate) + Base64URL で短縮し、QRコードでも渡せるようにする

### 制約（事前に理解が必要な点）
- **同一LAN内**：STUNなしでも接続できる可能性が高い
- **異なるネットワーク（インターネット越し）**：自分のグローバルIPを知るため **STUNサーバー**
  （例：Google公開STUN `stun:stun.l.google.com:19302`）が通常必要。STUNは接続時にアドレスを
  教えるだけでゲームデータは中継しないが、「外部サーバーを一切使わない」を厳密に解釈すると抵触する。
  → **設定でSTUNのON/OFFを切り替え可能にする**（デフォルトの扱いは要確認：§9）
- **対称型NAT（一部のモバイル回線・企業ネットワーク等）**：中継用のTURNサーバーがないと
  接続できない場合がある。本方針ではTURNは使わないため、**一部環境では接続不可**となる
- ゲームのHTML/JSファイル自体はどこかに置く必要がある（GitHub Pages等の静的ホスティング、
  またはローカルでファイルを開く）。これは通信用サーバーではない

### 通信を使わない複数人プレイ（補完）
- **ローカル同一画面モード**：1台のPCでキーボード（2人分）＋ゲームパッド（Gamepad API）で最大4人
- ネットワーク制約の影響を受けないため、確実に4人で遊べる手段として用意する

## 3. 技術スタック

| 項目 | 採用 | 理由 |
|------|------|------|
| 言語 | TypeScript | 型安全、ネットワークメッセージの型定義 |
| ビルド | Vite | 静的ファイル出力、開発サーバーが軽量 |
| 描画 | Canvas 2D | ベクター風線画に十分。依存なし |
| 通信 | WebRTC `RTCPeerConnection` + DataChannel（ブラウザ標準API） | P2P |
| 圧縮 | `CompressionStream`（ブラウザ標準） | SDP短縮 |
| QR | 軽量QRライブラリ（例：`qrcode` npm）※任意 | コード受け渡しの補助 |
| 音 | Web Audio API | 効果音をオシレーターで生成（音声ファイル不要） |
| テスト | Vitest | シミュレーションロジックの単体テスト |
| 配布 | GitHub Pages | 静的ファイルのみ |

ゲームエンジン等の大きな依存は使わない。

## 4. アーキテクチャ

```
src/
  main.ts              エントリ、画面遷移（タイトル/ロビー/ゲーム/リザルト）
  core/
    sim.ts             ゲームシミュレーション（純粋ロジック、描画・通信に非依存）
    entities.ts        Ship / Bullet / Asteroid / (UFO) の型と更新
    collision.ts       円判定（画面ループ考慮）
    rng.ts             シード付き乱数（再現性・テスト用）
    rules.ts           得点・残機・勝利条件
  input/
    keyboard.ts        複数プレイヤー用キー割当
    gamepad.ts         Gamepad API
    touch.ts           （任意）スマホ用仮想ボタン
  render/
    renderer.ts        Canvas描画、ベクター風エフェクト
    hud.ts             スコア・残機表示
  net/
    signaling.ts       offer/answer生成・圧縮・貼付け処理
    peer.ts            RTCPeerConnection/DataChannel管理
    protocol.ts        メッセージ型とエンコード
    host.ts            ホスト側：入力受信→シミュ→スナップショット配信
    client.ts          ゲスト側：入力送信→スナップショット補間
  audio/sfx.ts
  ui/lobby.ts          部屋作成/参加UI、コード表示・QR
```

**設計の核**：`core/sim.ts` は「入力 → 固定時間ステップで状態更新」だけを行う純粋ロジックにする。
ソロ・ローカル・オンライン全モードで同じシミュレーションを使い、違いは「入力がどこから来るか」
「誰がシミュレーションを回すか」だけにする。

### ゲームループ
- 固定タイムステップ 60Hz（accumulator方式）でシミュレーション、描画は `requestAnimationFrame`

## 5. オンライン同期方式：ホスト権威型

- **ホスト**がシミュレーションを唯一実行（チート・不整合の防止が容易）
- **ゲスト**は毎ティック入力（回転/推進/発射/ハイパースペースのビットフラグ＋シーケンス番号）を送信
- ホストは 20〜30Hz で**スナップショット**（全エンティティの位置・速度・角度、スコア）を配信
- ゲストは受信スナップショット間を**補間**して表示（約100msの表示遅延）
- 自機のみ**クライアント予測**を行い操作の遅延感を減らす（フェーズ4、任意）
- DataChannel は2本：
  - `state`：`ordered:false, maxRetransmits:0`（スナップショット・入力。古いものは捨てる）
  - `event`：信頼性あり順序保証（参加/退出、撃破、ゲーム開始/終了、チャット等）
- メッセージは最初JSON、帯域が問題になればバイナリ（`ArrayBuffer`/`DataView`）へ移行
- 切断検知：一定時間パケット無し→そのプレイヤーの船を除去、ゲームは継続
- ホストが切断した場合はゲーム終了（ホスト移譲はスコープ外）

## 6. ゲームデザイン

### 基本（原作準拠）
- 船：回転・推進（慣性）・発射・ハイパースペース（ランダムワープ、一定確率で自爆）
- 画面端は反対側へループ（船・弾・小惑星すべて）
- 小惑星：大 → 中2個 → 小2個 に分裂。全滅で次のウェーブ（数が増える）
- 弾：寿命あり、同時発射数に上限

### 得点（原作の値を参考）
| 対象 | 得点 |
|------|------|
| 大小惑星 | 20 |
| 中小惑星 | 50 |
| 小小惑星 | 100 |
| 他プレイヤー撃破 | 200（調整可） |
| （任意）UFO 大/小 | 200 / 1000 |

### 対戦ルール
- 各プレイヤー色分け（P1〜P4）
- 被弾・小惑星衝突で撃破 → 数秒後にリスポーン、**リスポーン直後は無敵（点滅）**
- 自分の弾は自分に当たらない
- 終了条件（要確認：§9）：案A 制限時間（例3分）で最高得点が勝ち / 案B 残機制で最後まで残った人 / 案C 目標スコア到達
- ソロは原作通り：残機制、ハイスコアを `localStorage` に保存

### 操作（ローカル時の割当案）
| | 回転 | 推進 | 発射 | ハイパー |
|---|---|---|---|---|
| P1 | A / D | W | Space | S |
| P2 | ← / → | ↑ | Enter（またはテンキー0） | ↓ |
| P3, P4 | ゲームパッド | | | |

※キーボードの同時押し制限（ゴースト）で2人同時操作が不安定な機種がある点に注意

## 8. テスト方針
- **単体テスト（Vitest）**：分裂・得点・衝突（画面ループ跨ぎ）・リスポーン無敵・終了判定。シード付き乱数で決定的に検証
- **プロトコル**：メッセージのエンコード/デコード往復テスト
- **P2P結合**：同一PCの複数タブ/ブラウザで手動確認。可能ならPlaywrightで2ページ間の接続を自動テスト
- **実機確認**：同一LAN、異なる回線（モバイルテザリング等）で接続可否を記録

## 10. リスク
| リスク | 影響 | 対策 |
|--------|------|------|
| NAT環境によりP2P接続不可 | オンライン対戦できない | ローカルモードの提供、接続失敗時の原因表示（STUN OFF/対称NATの可能性） |
| 手動コード交換が面倒 | UX低下 | 圧縮＋QRコード、ワンクリックコピー、ゲスト毎に並行して受け渡し可能に |
| ホストの回線・性能に依存 | ゲストのラグ | スナップショット頻度調整、補間、バイナリ化 |
| キーボードのゴースト | ローカル2人操作不安定 | ゲームパッド推奨、キー割当変更機能 |
